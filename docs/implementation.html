VUGVA Integration — Implementation Status

Version: integration 0.2.0 · vendored llama.cpp b12119 (3de52ac3, 2026-11-04) · VUGVA core 898e5e1 · paper DOI 10.5281/zenodo.21549808. See README.md (version matrix) and docs/ for user-facing docs and CHANGELOG.md for the history.

This file previously described a plan to make VUGVA a compute backend in the llama.cpp scheduler (supports_op=true, VUGVA claims every op, delegates to CUDA). That approach was tried and reverted: it produced >1000 graph splits and crashed in sched_reserve. The architecture below is what actually ships and is verified to run.

Architecture (current)

VUGVA is a buffer type + memory tier manager, never a compute backend:

GGUF file ──mmap──► VUGVA_DRAM buffer (warm tier, pool-accounted)
                      │
                      ├─ hot: layers capped to free VRAM ─► CUDA0 buffer (VRAM)
                      ├─ warm: everything else          ─► VUGVA_DRAM (page cache / pinned)
                      └─ cold: pool budget exceeded     ─► SSD via page cache (mmap file)

compute: CUDA runs the hot-tier layers; DRAM-tier weights are read directly by
the CPU backend; llama.cpp's op_offload moves small/batched ops to CUDA.

Key properties enforced in ggml-vugva/ggml-backend-vugva.cpp:

Hook Behavior Why
dev.supports_op true consulted only by weight_buft_supported()/select_buft() for weight placement. VUGVA is skipped as a scheduler backend in llama-context.cpp and has graph_compute = NULL, so it never executes ops.
dev.get_buffer_type singleton per device llama.cpp compares buffer-type pointers (is_default_buft); a fresh instance per call broke the mmap zero-copy import and leaked.
dev.get_host_buffer_type NULL otherwise llama.cpp's "avoid host buffers when using mmap" rule rewrites every VUGVA selection back to the plain CPU buffer.
buft.alloc_buffer pool-accounted (vugva_alloc), cudaMallocHost storage, anonymous-mmap fallback page-locked memory ⇒ scheduler H2D copies are true DMA (paper §5.1); allocation must not fail when the pool is merely over budget.
dev.buffer_from_host_ptr wraps the GGUF mmap range default load mode: zero-copy weights, page cache = DRAM tier, file = cold tier. Over-budget imports are accepted with a logged warning.
buft.get_max_size SIZE_MAX used by ggml to chunk allocations, not as a capacity gate.

Placement changes in llama.cpp/src/llama-model.cpp:

  1. make_gpu_buft_list() does not prepend VUGVA (an earlier revision did — that sent even -ngl layers to DRAM and left the GPU idle). VUGVA enters as the first entry of make_cpu_buft_list() via the generic ACCEL loop, which is appended as fallback: GPU layers keep CUDA first, everything else lands in VUGVA_DRAM (input layer, non-offloaded layers, KV of those layers).

  2. Algorithm 1 / VRAM budget in load_tensors(): before assigning layers, free VRAM minus a reserve (max(1 GiB, total/8)) is compared against per-layer weight sizes (blk.N.* from the GGUF). Requested layers that no longer fit fall back to the DRAM tier instead of aborting with cudaMalloc failed: out of memory. The output layer is budgeted first (largest matmul per token). Logged as:

    load_tensors: [VUGVA] VRAM budget 5973 MiB (free 6997, reserve 1024) -> 10/41 layers + output on GPU, remainder -> VUGVA_DRAM tier (requested -ngl 99)

Root causes fixed (the original broken state)

  1. dev.supports_op returned false → every tensor rejected VUGVA_DRAM → weights fell through to the CUDA buffer type → one contiguous 19.9 GB cudaMalloc → OOM on the 8 GB card (the reported 35B failure).
  2. get_buffer_type allocated a new instance per call → is_default_buft never matched → mmap zero-copy import path was dead, plus a leak per call.
  3. make_gpu_buft_list() prepended VUGVA before CUDA → with (1) fixed, all weights (including -ngl layers) would have gone to DRAM, GPU idle.
  4. get_host_buffer_type() returned VUGVA's own buft → llama.cpp's mmap rule silently rewrote VUGVA selections to the CPU buffer.
  5. vugva_alloc failure (pool over budget) hard-failed the import → any model larger than the pool could not load at all.
  6. get_max_size() returned the 32 GB pool size (ggml uses it to chunk).
  7. tests/test_vugva.cpp built a std::vector from the negated return of llama_tokenize → std::length_error abort; it also forced n_gpu_layers=0.
  8. CMake VUGVA_DRAM_GB was never wired into the backend (32 GB hardcoded), and the vugva_test target referenced by README/CI/CONTRIBUTING did not exist.

Mode selection (llama-model.cpp, Algorithm-1 block)

  • Hot tier is a contiguous prefix of the requested layers (no holes, so no extra graph splits); the output layer is budgeted first and its tied embedding is counted (llama.cpp duplicates token_embd into the output buffer via TENSOR_DUPLICATED).
  • Tensors rewritten by --cpu-moe / -ncmoe (tensor_buft_overrides) are excluded from the hot-tier budget, so MoE models can keep all attention/SSM layers in VRAM.
  • auto picks zerocopy only when the estimated warm tier fits in RAM with a 25%/4 GiB margin and stays below 50% of physical RAM; otherwise hybrid.
  • Pinned allocations are capped (50% RAM, ≥2 GiB headroom, VUGVA_PIN_MB) and a failed mapped allocation downgrades the run to hybrid instead of crashing.
  • CPU-buft overrides (--cpu-moe) now use the plain CPU buffer (mmap-backed) instead of the VUGVA DRAM tier, avoiding a full copy of the expert stack.

Paper vs. code: what is implemented, what is not

Three of the paper's mechanisms are implemented; one is partially implemented; one cannot be implemented in llama.cpp's execution model, and one is hardware gated. Everything below is reproduced on the reference machine (RTX 4060 8 GB, 29 GB RAM, NVMe, CUDA 13.2) with the numbers from docs/benchmarks.md.

Paper claim Status Where
Three-tier placement VRAM → DRAM → SSD (§3.1) implemented llama-model.cpp Algorithm 1 block, VUGVA_DRAM buft
CPU-bypass data plane (§5.1) implemented (load + zero-copy reads) mapped pinned DRAM + UVA
Algorithm 1: static placement into the hot tier implemented contiguous hot prefix, tied-embedding aware
Algorithm 2: membrane-driven promotion / eviction implemented, opt-in VUGVA_HOT_CACHE_MB, tier manager below
Algorithm 3: look-ahead prefetch partially implemented (cold tier) VUGVA_PRELOAD; DRAM→VRAM pipelining deliberately absent
GPUDirect Storage / IOMMU P2P cold tier not available on this hardware, probed at runtime ggml_backend_vugva_probe_cold_tier
Paper's aggregate numbers (+54.8% throughput, −84.6% CPU) not reproduced; different hardware and workload our own table below

1. Promotion / eviction of individual tensors — implemented (opt-in)

ggml-vugva/ggml-backend-vugva.cpp → Tier manager, called from llama_context::graph_compute (tier_begin before the scheduler runs, tier_end after it is enqueued).

  • On each decode step the graph's leaf weight tensors in VUGVA_DRAM are walked in graph (layer) order, which is the paper's look-ahead order.
  • A miss allocates a VRAM slot, cudaMemcpyAsyncs the tensor on a dedicated non-blocking stream and redirects tensor->data to it. A hit just bumps the LRU clock. Under budget pressure the least-recently-used slot is evicted and its tensor is pointed back at DRAM.
  • Redirection is stable across steps: llama.cpp's CUDA-graph cache keys on source pointers, so moving a pointer every step would disable graph capture. Pointers change only on promotion and eviction.
  • The cache refuses to enable when static placement already filled VRAM (VUGVA_HOT_CACHE_MB > free VRAM ⇒ warn and stay static), because that pathological case is measurable: 27B, 17.4 GB, 512 MiB cache on a full card ran at 0.60 t/s vs 1.20 t/s static. With the gate, the same command reports hot cache ignored: only 961 MiB VRAM free and keeps 1.20 t/s.

Measured effect (Qwen3.5 0.8B Q4_K_M, static budget forced to 100 MiB so only 8/25 layers are hot, greedy, 24 tokens, identical output text in all runs):

VUGVA_HOT_CACHE_MB promoted evictions decode
0 (static only) – – 25.3 t/s
64 2708 MiB 2912 18.5 t/s (thrashing, as expected when the cache is smaller than the working set)
2048 394 MiB 0 149.1 t/s (5.9× over static, ≈ full-GPU speed of 202 t/s)

So the membrane behaves as the paper describes: gain when the cache holds the per-token working set, loss when it does not — and the loss is visible in the counters (VUGVA_STATS=1) instead of hiding as "it feels slow".

2. Look-Ahead prefetch (Algorithm 3) — partially implemented

Implemented: cold-tier readahead. VUGVA_PRELOAD (default on) starts a background thread after the model loads and issues posix_fadvise(..., POSIX_FADV_WILLNEED) over the GGUF in 64 MiB chunks, 20 ms apart, stopping below 2 GiB of MemAvailable. It is the tier that actually reads from NVMe (the experts of a sparse MoE), it cannot pin memory (clean file pages are reclaimable), and it reports progress:

[vugva] cold-tier prefetch: 4480/20707 MiB read ahead (22%)

Not implemented: pipelined DRAM → VRAM weight streaming. This is not an omission that a few more lines would fix; the llama.cpp execution model excludes it:

  • every kernel of a decode step is enqueued before any of them executes, so the weight pointer of layer k must be final at enqueue time. A copy issued "while layer k−1 computes" would therefore have to be part of the graph.
  • a copy placed in the compute stream serializes with the kernels — that is exactly the hybrid path, measured at 0.85–1.2 t/s on the 27B versus 1.20 t/s for direct zero-copy reads.
  • a copy on a second stream cannot be joined per layer, because ggml graphs have no event-wait op. The only way to overlap would be to make VUGVA a compute backend, which was tried and reverted (>1000 graph splits, sched_reserve crash — see above).

Zero-copy already achieves Algorithm 3's goal (keep the CPU out of the data plane): the GPU reads warm-tier weights from pinned DRAM over PCIe with the CPU idle. Adding promotion on top can only add traffic.

3. GPUDirect Storage / IOMMU P2P — not available here (probed, not assumed)

ggml_backend_vugva_probe_cold_tier() runs at startup and prints one line:

[VUGVA] cold tier: cufile=yes pageable_access=yes host_ptr_p2p=yes iommu=no -> cold tier: OS page cache (GGUF mmap)

libcufile is installed and the GPU can address host memory, but there is no IOMMU group for the NVMe controller, so a cuFile read would bounce through host memory — faster-looking code, same traffic. The probe only reports GDS eligible when libcufile, pageable access and an IOMMU are all present. Wiring cuFile into the loader is not implemented; the cold tier is the page cache over the GGUF mapping, as stated.

4. The paper's measured numbers are not reproduced

The paper reports +54.8 % throughput and −84.6 % CPU on a non-NVLink multi-GPU cluster. This repository's measurements are single-GPU and are reported as such (docs/benchmarks.md); no number in this repo is derived from, or asserted to reproduce, the paper's aggregate figures. The CPU-bypass property that the paper quantifies is visible here as scheduler behaviour instead: graph splits = 1 and the CPU backend executing no layer, rather than as a percentage.

Pool accounting

The Rust TieredPool (/home/irfan/Desktop/VUGVA/vugva) provides NUMA-local registration and bookkeeping (vugva_alloc/vugva_dealloc/vugva_pool_info); the ggml buffer owns the actual storage (mmap import or cudaMallocHost). Pool size: cmake -DVUGVA_DRAM_GB=N, runtime override VUGVA_DRAM_GB=N. Note: the pool attempts a whole-range cuMemHostRegister at creation; on a 32 GB machine registering 32 GB fails harmlessly (bookkeeping still works).
