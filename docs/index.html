Virtual Unified GPU VRAM Architecture

Run models larger than your VRAM — without leaving llama.cpp.

VUGVA splits the model across three tiers — VRAM hot, pinned DRAM warm, NVMe cold — and keeps CUDA as the compute engine. A 35B mixture-of-experts model runs on an 8 GB card at 20–40 tok/s; a 27B dense model runs at all.

How it works

A buffer type and a placement policy — never a compute backend.

Algorithm 1

Budgeted hot block

Measures free VRAM, keeps a reserve, fills a contiguous layer prefix and spills the remainder to the DRAM tier instead of failing with CUDA OOM.

 zerocopy

GPU reads DRAM over PCIe

Pinned, UVA-mapped warm tier is addressable by the CUDA backend, so the scheduler sees one device: one graph split, no copies, CPU idle.

 MoE

Sparse experts stay in mmap

Only a few experts are active per token, so copying 20 GB is wasted work. Attention stays hot, experts are paged in from the file cache.

 VUGVA_HOT_CACHE_MB

Runtime promotion cache

Warm weights are promoted into leftover VRAM on first use and LRU-evicted under a byte budget. Counters show hits, misses and thrash.

 Safety

Pinning cannot OOM you

Pinned memory is capped at 50 % of RAM with 2 GiB headroom; a refused pin degrades to pageable DRAM, never to swap soup.

Quick start

Two builds: the Rust VUGVA core, then llama.cpp against it.

# 1 · VUGVA core (DRAM pool + tier bookkeeping)
git clone https://github.com/Mr-DS-ML-85/VUGVA.git
cd VUGVA/vugva && cargo build --release

# 2 · llama.cpp + VUGVA
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON \
      -DVUGVA_DIR=$PWD/../VUGVA/vugva
cmake --build build -j

# 3 · a model that fits: nothing changes
./build/llama-cli -m qwen3.5-0.8b.gguf -ngl 99 "The capital of France is" -n 24

# 4 · a 35B MoE on an 8 GB card: experts go to mmap automatically
./build/llama-cli -m ornith-35b-moe.gguf -ngl 99 -ctk q4_0 -ctv q4_0 \
    --temp 0.7 "Explain why the sky is blue" -n 64
→ decoded 48 tokens in 1.20 s, speed: 40.16 t/s
